## 1. Tier F / Tier P

The policy is T-1 to T-9 as approved; this section fixes how the tools carry
it.

### 1.1 Tier assessment (T-4)

At step 2 the release records `TIER_ASSESSMENT.md` in the staging directory:
the diff `SOURCE_CANDIDATE` against the last release tag, whether any T-1
trigger applies (each trigger answered yes/no with evidence), the OS-specific
targets T-3 adds, the ABI comparison with the last Tier F artifact
(`DT_NEEDED`, highest `GLIBC_` and OpenSSL versions), and for each updated
statically linked SSH, crypto or compression dependency whether it is reached
at run time. The independent review checks it; the Owner approves the tier.
The approved tier is written into the R8 contract (§1.3) and the manifest
(§1.2).

### 1.2 Manifest schema `sinter-acceptance-manifest/2`

Schema `/1` stays verifiable for published releases. `/2` adds:

| Field | Rule |
|---|---|
| `acceptance_scope` | `full` or `patch` |
| `full_reference` | patch only: `{version, manifest_sha256, finished_at, releases_since}`. The checker gets the reference manifest with `--full-reference <file>`, checks its SHA-256, that it is a `full` GO manifest, that `run.started_at` is at most 60 days after its `finished_at`, and that `releases_since` (the versions published since, recorded at step 2 and reviewed) has at most two entries |
| `abi` | `{dt_needed: [...], max_glibc, max_openssl}` measured on the frozen executable; patch: equal to the reference manifest's `abi` |
| `required_targets` | full: exactly the eight targets. patch: `ubuntu2404`, `rocky9`, the first available of `ubuntu2604`, `rocky10`, `rhel10`, `alma10`, plus every T-3 target of the assessment |
| `targets[].checks.not_applicable` | integer; `passed + failed + skipped + not_applicable == total` |
| `targets[].not_applicable_checks` | list of `{id, reason}`; see §2 |

Checker rules added for `/2` (FAIL stops the release as today):
- every `required_targets` label is present, and no other label;
- `skipped == 0` on every target (today only the harness's raw verdict
  enforces this; the checker accepts `skipped > 0`, which `/2` closes);
- a target is PASS only if `failed == 0`, `skipped == 0`, `total > 0`, and
  every not-applicable check is allowed by §2 and proven in its log;
- `totals` add `not_applicable`; the overall verdict is GO only if every
  required target is PASS. Not-applicable checks are never counted as passed.

### 1.3 R8 runner (T-6)

The p5 contract gains `P5_TARGETS` (comma-separated labels; default the eight)
and `ACCEPTANCE_SCOPE`. The contract verifier refuses a set that is not a
subset of the eight, a `full` scope with fewer than eight, and a `patch` set
that misses a required target. Both values are part of the approval string, so
an approval for eight targets never covers fewer. Tests and an independent
review are required (T-6).

### 1.4 Release notes and NOT RUN (T-8)

The release notes state the tier. For Tier P they name the reference Tier F
release and manifest SHA-256 and list the targets not run in this release as
NOT RUN (never PASS). The supported targets stay the eight (T-9).

## 2. NOT APPLICABLE (D-8)

- Allowed only for pairs listed in `release/acceptance-harness/applicability.json`
  (a harness file, so its SHA-256 is in the manifest and it is reviewed with
  the harness). v1.15.0 lists only the `nm_connection` checks, with the single reason
  `NM_NOT_INSTALLED`, and names the targets for which it may be used (D-8:
  an OS where nmcli is not available).
- The harness first runs a fixed observation and logs it:
  `== observe nm-presence nmcli=<present|absent> service=<active|inactive|not-found>`.
  It emits `== check <id> NOT_APPLICABLE NM_NOT_INSTALLED` only when that
  observation shows no `nmcli` and the table lists the target. Otherwise the
  check runs and passes or fails (an installed but stopped NetworkManager
  fails the check).
- The raw verdict (`raw-verdict.py`) derives each target's expected ids as the
  expected list minus the proven not-applicable pairs, and fails a
  `NOT_APPLICABLE` line that is not in the table or not proven. The checker
  repeats the check from the bundled log and table.
- A target whose image is expected to have NetworkManager but does not is not
  "not applicable" by assumption: the table names the reason, and the log
  proves it on each run.

## 3. New acceptance checks for v1.15.0

All run with the frozen artifact on every target unless marked; each runs
on disposable state and removes it.

| Id | What it shows |
|---|---|
| `timer-create`, `timer-idempotent`, `timer-running`, `timer-absent` | unit written, daemon-reload, enabled and active, second run unchanged, removal leaves `not-found` |
| `timer-calendar-invalid` | an invalid `OnCalendar` fails in plan and apply with no change |
| `service-timer-name` | the existing `service` type manages `<x>.timer` |
| `fw03-interface`, `fw03-source`, `fw03-zone`, `fw03-reload` | firewalld 0.3.0 on a disposable zone with a dummy interface and a documentation network (`198.51.100.0/24`), runtime and permanent, idempotent, removed |
| `risk-static-refusal` | an R resource without approval is exit 2 before contact |
| `risk-approved-apply` | plan with `--approval-request`, `sinter approve` driven through a pseudo-terminal by the harness (Python `pty`; P7-R1, instead of `script`), apply with `--approval` on a disposable zone whose path result is `clear`; a second apply with the same approval is refused (used); also refused: no approval, an altered request, and the approval of one change used for another (§3.1) |
| `fw03-no-residue` | P7-R1: after the firewalld checks, zones (runtime and permanent), every file under `/etc/firewalld` and the dummy interface are as before, and the VM's management path is unchanged (§3.1) |
| `nm-profile-crud` | an inactive Ethernet profile for a non-existent interface is created, changed, verified and deleted; not applicable as in §2 |
| `discover-readonly` | discover on the target writes the recipe and provenance, a planted synthetic secret file is excluded, and package database and `/etc` digests are unchanged |
| `discover-roundtrip` | audit of the generated recipe on the unchanged target reports no drift |

firewalld on the Ubuntu targets: firewalld is not part of those images by
default (to be confirmed per image). The harness installs and starts it in
target preparation on the disposable VM (the default zone allows SSH), and
checks a new SSH session before the firewalld checks; if that check fails the
target fails. If the Owner prefers not to install firewalld there, extending
§2 to firewalld needs a separate decision; it is not assumed.

The firewalld 0.3.0 types are R or C (DESIGN §43.2), so `fw03-interface`,
`fw03-source`, `fw03-zone` and `fw03-reload` run through the same approval flow as
`risk-approved-apply`. The harness reaches the target over SSH to `127.0.0.1` and passes
`--management-path loopback` (it connects directly, on the same VM, so the
declaration is true), so the management path is `lo` (DESIGN §43.3) and the
results are `clear`; `fw03-reload` additionally needs the P3 measurement that
loopback traffic is accepted whatever the zones (otherwise it is unknown and the
check is redesigned before P8; §3.2 R-2). The matrix does not test real management-path
detection, which is tested on dedicated hosts (§5). The harness drives `sinter approve` through a pseudo-terminal: this tests the
flow, and shows again that a terminal is not proof that a person approved
(DESIGN §43.4). Activation of NetworkManager profiles, checkpoints and the guarded procedures
of DESIGN §43.6 are not part of the release matrix: they are tested on
dedicated disposable hosts (§5) and the evidence is reviewed separately, as
was done for firewalld 0.1.0 and 0.2.0.

### 3.1 firewalld 0.3.0 checks in the harness (P7-R1)

Owner decision of 2026-11-20: firewalld 0.3.0 is measured on real hosts and
registered (option a); a redesign on another R resource is considered only if
that fails (option b); releasing without testing `sinter approve` on real
targets is not accepted (option c rejected). The five checks are therefore
never SKIP, PASS or NOT APPLICABLE without running.

The `fw03-checks` section of `acceptance-target.sh`:

- Prerequisites, logged as `== observe fw03-presence firewall-cmd=<present|absent> state=<...> plugin030=<embedded|absent>`:
  a running firewalld (target preparation installs and starts it where it is
  missing; unless the zone of the default-route interface allows `ssh` or
  22/tcp and a new loopback SSH session works, it puts firewalld back as it
  was and stops the preparation), firewalld 0.3.0 embedded in the sinter
  under test (`sinter plugin list`), a usable management path, the disposable
  names unused (zone listed at runtime or permanent, a zone file or its
  `.xml.old`, the interface), and no address of the VM or of the session's
  client inside the documentation networks (the declared loopback path does
  not protect them). Any of them missing: all six checks FAIL, and nothing is
  created or removed.
- Disposable objects only: zone `sintacc`, dummy interface `sintacc0`
  (NetworkManager told not to manage it, so the §44.7 rule can judge its
  permanent binding), networks `198.51.100.0/24`, `192.0.2.0/24`,
  `203.0.113.0/24`, ports `8471/tcp`, `8472/tcp`. No recipe names the VM's
  default-route interface or its zone.
- Management path: before the section and after every change, the
  default-route device, its zone, that zone's runtime and permanent
  configuration, every other zone except the disposable one (runtime and
  permanent), policies and direct rules are recorded, and a new SSH session to
  `127.0.0.1` with the pinned host key is opened; any difference fails the
  step's check, before a later reload could hide a runtime-only change. The
  loopback session shows that sshd answers, not that the runner's route is
  open; the zone configuration is what detects a change on that route.
- `fw03-zone`: zone present (N, no approval), unchanged on a second apply;
  later absent with an approval (R), gone at runtime after a reload. The
  harness makes the new zone active with a direct `firewall-cmd --reload`, so
  `fw03-interface` and `fw03-source` do not depend on `fw03-reload`.
- `fw03-interface`, `fw03-source`: present, present again (`none`), absent;
  each run through plan with a request, approve on a pseudo-terminal and apply
  with the approval; runtime and permanent queries after each step.
- `risk-approved-apply`: refused without an approval (exit 2, before
  contact); `sinter approve` refuses a pipe (no terminal) and a wrong digest
  prefix and records no approval; an altered request is refused by
  `sinter approve` for its integrity check; the approval of
  one source used for another source fails the re-plan (exit 5, nothing
  changed); the approved apply changes the source; the same approval again is
  refused (exit 2, `already been used`); `sinter approvals list` shows it
  `used`; the removal is approved and applied.
- `fw03-reload`: a port added permanently by the harness (not at runtime)
  becomes active when a resource change notifies the `plugin` reload handler;
  the handler reports plugin provenance; a second apply notifies nothing.
- `fw03-no-residue`: after `fw03_restore` (direct removal of everything above,
  including the `.xml.old` file firewalld leaves when a zone is deleted, and a
  reload), every zone (runtime and permanent), ipsets, policies, direct rules,
  every file under `/etc/firewalld`, NetworkManager's profiles, the dummy
  interface and the management path equal the state before. `fw03_restore`
  runs only when the section itself ran; a harness killed in the middle leaves
  the disposable objects on the (disposable) VM. The approval ledger's events
  are logged (`FW03_LEDGER`) before the section's approval store is removed.

Mock tests: `release/tests/test_acceptance_fw03_checks.py` runs the section
against fakes and makes each rule break once.

### 3.2 Product prerequisites before the checks can pass

Status (P7-R3 complete, 2026-11-21; independent final audit GO, 0 BLOCKER):
R-1, R-2, R-4 and R-5 are implemented (DESIGN §44.7); R-3 stays as measured
(the dummy interface is unmanaged). History: in P7-R2 (2026-11-20) a loopback
reload also needed the measured permanent configuration (no direct rule or
passthrough, only the policy `allow-host-ipv6`; independent audit B-1), so
`fw03-reload` failed on Rocky Linux 10.2, whose image has five further
permanent `gateway-*` policies. P7-R3 replaced the "only `allow-host-ipv6`"
condition with this rule (DESIGN §44.7, R-2): every permanent policy's
definition is read (`--permanent --info-policy=<p>`) when the path is
determined and again at the reload's turn; `allow-host-ipv6` must equal the
definition measured for the version byte for byte; a further policy is
accepted only on firewalld 2.4.3 and only when its definition has exactly one
`disable` line, `  disable: yes`. An enabled, unreadable or malformed policy,
a disabled policy on another version, a changed `allow-host-ipv6`, a
direct rule or passthrough, or an unmeasured version stays unknown and the
reload is refused.

P7-R3 re-measurement (2026-11-21, four disposable VMs, deleted after their
evidence was verified): on Rocky Linux 10.2 the disabled `gateway-*` policies
are absent from the nftables ruleset before and after a reload (the
`allow-host-ipv6` chains present as the positive control); every policy
definition is stable and byte-identical to its fixture (18 comparisons); the
release harness with the P7-R3 build passed 76/76 on Rocky Linux 9.8 and
10.2 and 75 with one NOT APPLICABLE (`nm-profile-crud`, `NM_NOT_INSTALLED`)
on Ubuntu 24.04 and 26.04, and `fw03-reload` passed on all four. These are
measurements of these four images only: they give no assurance for other
EL10 distributions (RHEL 10, AlmaLinux 10) or other images, whose
configurations stay unknown and refused unless they are the measured ones;
the release acceptance of §3 is what runs the frozen artifact there.

Known limit (Owner decision of 2026-11-21, unchanged): with a
NetworkManager-managed management interface (the measured Rocky Linux images),
permanent firewalld changes on a real (non-loopback) management path, and a
reload judged on that path's permanent configuration, are refused as unknown.

The checks run the product; they pass only after these reviewed changes,
each made after its measurement (§3.3), never before:

- **R-1 registration of firewalld 0.3.0** (DESIGN §38.4, §44.3): the measured
  catalog and plugin bytes move from `plugins/first-party/candidates/` to
  `catalogs/` and `plugins/`, `FIRST_PARTY_CATALOGS` gains the entry with the
  digest of the measured bytes, the embedded bundle, the connection-risk
  classification table (bound to the catalog digest, DESIGN §43.7) and the
  README follow.
  Any exit status or behaviour that differs from the candidate changes the
  bytes (a new candidate digest) or the Core, not the measurement.
  *Done in P7-R2: every exit status matched and 0.3.0 is registered with the
  candidate's bytes.*
- **R-2 reload on a declared loopback path** (§44.4): `loopback_reload_measured`
  is `false`, so the reload handler is `unknown` on the matrix's loopback path
  and `fw03-reload` fails by design today. If M-RL (§3.3) shows on every
  measured firewalld version that loopback traffic is accepted whatever the
  zones and across a reload, the Core sets it only for those versions (a
  fixed read-only `firewall-cmd --version` observation; any other version
  stays `unknown`). If not, `fw03-reload` is redesigned on a measured
  non-loopback path before P8.
  *Done in P7-R2 and P7-R3: M-RL held on the four measured versions; the
  reload is `clear` only under the measured-configuration rule stated in the
  status above (DESIGN §44.7, R-2), and `fw03-reload` passed on all four in
  the P7-R3 re-measurement.*
- **R-3 NetworkManager-managed interfaces** (§44.7): the harness marks the
  dummy interface unmanaged; if M-NM shows that `nmcli device set ... managed no`
  does not make the binding judgeable, the check is changed, not the rule.

- **R-4 `ss` program path** (§43.3, measured): `ss` is `/usr/sbin/ss` on Rocky
  Linux 9 and 10 (no `/usr/bin/ss`) and `/usr/bin/ss` on Ubuntu 24.04 and
  26.04. The Core reads only `/usr/bin/ss`, so on the EL targets every
  non-loopback management path is `unknown` and every C or R change is
  refused. Fail-closed, but the control is unusable there; a reviewed fixed
  list of measured paths is needed. Not needed by the matrix (loopback).
  *Done in P7-R2: the two measured paths, root-owned and not writable by
  group or others (DESIGN §44.7, R-4).*
- **R-5 runtime zone priority** (§44.7, measured): `firewall-cmd --zone=<z>
  --get-priority` without `--permanent` is a usage error (exit 2) on firewalld
  1.3.4, 2.1.1, 2.3.1 and 2.4.3; with `--permanent` it answers on 2.x and is
  a usage error on 1.3.4. The Core reads the runtime priority with the runtime
  form (and the permanent one with `--permanent`), so the runtime management
  zone is `unknown` on every measured host and every C or R change on a real
  path is refused. Needs a design decision (read the priority from
  `--list-all`, which shows `ingress-priority` on 2.x, or use the permanent
  value) and a reviewed change. Not needed by the matrix (loopback), but the
  guarded procedure (M-G) cannot be exercised until R-4 and R-5 are made.
  *Done in P7-R2: the priority is read from `--list-all` of the same view
  (DESIGN §44.7, R-5); the guarded procedure was then measured on Ubuntu
  24.04 and 26.04.*

## 4. Publish order (D-9)

### 4.1 Problem

The release-candidate commit raises `Cargo.toml`; the WebMCP metadata
(`docs-site/src/data/resources.json` version, `build-webmcp.ts` release and
artifact) changes only in the post-publish docs commit, because the docs must
not announce a version before its Release exists. When `main` is pushed to the
RC (step 14–16 command 4, `git push <remote> main`) and the pushed range
touches `docs-site/**`, the documentation workflow runs `webmcp:check`, which
fails on the version mismatch (v1.10.0, v1.12.0, v1.14.1). The check is
correct and stays unchanged.

### 4.2 New order

| Step | Change |
|---|---|
| 12b (new, before the review) | Create the docs commit `D` with parent `RC_COMMIT`: version references, WebMCP metadata, installer and dev-container version, `start.yml` version check, and `release/evidence/v${VERSION}/acceptance-manifest.json` copied from the staged manifest. Check it locally only: the documentation `check`, `webmcp:check`, `tutorial:check` and `build`, and the CI checks that need no Release (examples, public tree). `D` is not pushed to any public branch before the Release exists: it announces the new version, and its dev-container change would start `start.yml`, which downloads the Release asset and must fail before publication. The documentation workflow's manual dispatch is never used on a branch (its deploy job would publish that branch). |
| 13 | The approval set gains `D` (§4.3). The Owner's approval covers tag, Release, assets, `D` and the fast-forward of `main` to `D`. Changing `D` needs a new approval. |
| 14 | `git fetch`; annotated tag at `RC_COMMIT`; `rev-parse TAG^{commit} == RC_COMMIT`; push the tag only; read back. `main` does not move. CI and advisories run on the tag push (their `on: push` has no filter); their results are recorded at 17c. |
| 15–16 | Unchanged. |
| 17a | Unchanged read-back, plus: the manifest copy in `D` is byte-identical to the downloaded asset. |
| 17b (new) | Push `D` to a work branch; CI and Start environment (now able to download the Release) must pass. Then `git fetch`, check `merge-base --is-ancestor origin/main RC_COMMIT` and `D^ == RC_COMMIT`, and push `D:refs/heads/main` without force: one fast-forward. The documentation workflow runs once, with matching versions. |
| 17c (new) | Record the results of CI on the tag, CI/Start/advisories/docs deploy on `main`, and the site's and `/webmcp.json`'s version. |

### 4.3 Approval set `sinter-approval-set/3`

`/2` plus `docs-commit/D.patch` (`git format-patch -1 D` output) and META
fields `docs_commit`, `docs_tree`. `verify_approval_set.py` checks: `D` exists,
its parent is `rc_commit`, its tree is `docs_tree`, the patch reproduces it,
every path `D` touches is in the docs allow-list (`docs-site/**`,
`README.md`, `README.ja.md`, `.devcontainer/install-sinter.sh`,
`.github/workflows/start.yml`, `examples/start/README*.md`,
`release/evidence/v${VERSION}/acceptance-manifest.json`),
and the manifest copy in `D` equals the approved acceptance manifest.

### 4.4 Runbook text to change (P7)

State machine rows 13 (allowed change: creating `D`, not pushing it), 14–16
(tag and Release only; `main` is not pushed), 17 (17a–17c); the Steps 14–16
command block (command 4 moves to 17b; `git fetch` before the tag and before
17b); Step 17 checklist; the approval-set section (`/3`); Abort rules (add:
`D` changed after approval, `D` pushed publicly before the Release). Moving
the `main` push from steps 14–16 to step 17 changes the order across steps;
the "Future fast path" rule that steps are never reordered is amended by the
same reviewed change, not bypassed.

### 4.5 Failure and recovery

| Failure | State | Recovery |
|---|---|---|
| Tag push fails | Nothing public | Read back `ls-remote`; fix and push the tag; never retag a different commit |
| Release creation or asset upload fails | Tag public | Existing "Partial publish failure": resume the unfinished steps; never delete or move the tag |
| 17a mismatch | Release public, `main` unchanged | Incident; do not push `D`; no force-fix |
| 17b work-branch CI fails | Release public, `main` unchanged | Fix forward with a new `D'` (parent `RC_COMMIT`), re-review `D'`; the docs keep showing the previous version meanwhile |
| `main` is not an ancestor of `RC_COMMIT` (moved meanwhile) | Release public | No force. Merge `RC_COMMIT` into the new `main` with `--no-ff` (v1.11.0 precedent) and put `D'` on that merge. `D'` no longer has `RC_COMMIT` as parent, so it fails the §4.3 rule: a new approval set records `docs_base` (the merge, whose parents must include `RC_COMMIT`), and the Owner approves it before `D'` is pushed |
| Documentation deploy fails after 17b | `main` updated | The previous site stays published; fix forward with a docs-only commit |

### 4.6 Version shown before publication

Until 17b, `main` and the site show the previous version and the Release page
shows the new one as Latest; nothing announces an unpublished version. The RC
branch carries the new `Cargo.toml`, but the documentation workflow runs only
on `main`.

## 5. Real-host testing (D-7)

Design only; no host, network or disk is created by this document. Before any
run, the operator presents the hosts, images, networks, expected cost, time
limit and deletion conditions for approval; every disposable resource is
deleted after its evidence has been verified.

- timer, firewalld 0.3.0 measurement (§38.4) and discover: one disposable host
  per family during development; release acceptance as §3.
- `nm_connection` activation, management-path detection and checkpoint:
  a disposable host with two network interfaces, each in a separate VPC
  network (management and test), and an out-of-band serial console. Activation is
  tested on the test interface; the checkpoint rollback is tested on the
  management interface only on this host, with the console open. Expected
  results include the indeterminate outcome when the connection cannot be
  re-established; such a host is deleted, never repaired in place.
- VLAN (only if D-11 later includes it): profile and device on the test
  interface as parent; tagged traffic is not tested.
