# OpenStack 2026.1 (Gazpacho) on Rocky Linux 10.2 — Sinter recipes

A port of [hagistack](https://github.com/hagix9/hagistack)'s `rocky10.2/` installer
(reference commit `8225c50c0b283bcdce960d64f7f7dfe32f5afc1c`) to Sinter recipes.

> **Demonstration setup, not a production recommendation.** It installs a working OpenStack for evaluating Sinter
> on a real workload; it does not make a hardened deployment. Read "Security limitations" before you run it.

**Step-by-step tutorial:** [Build OpenStack 2026.1 with Sinter](https://sinter.fulltrust.co.jp/en/tutorials/openstack-aio/overview/)
([日本語](https://sinter.fulltrust.co.jp/ja/tutorials/openstack-aio/overview/)) walks through these recipes on a builder and
an all-in-one node, with the commands of the real-host acceptance. This README stays the technical reference.

## Requirements

* **Target:** one Rocky Linux 10.2 x86_64 host for the all-in-one layout (the only layout accepted on a real host),
  with at least 4 vCPUs, 16 GB RAM, about 50 GB free disk, and `/dev/kvm` (nested virtualization on a cloud VM) for
  `virt_type: kvm`. The accepted run used a GCE `n2-standard-4` with a 60 GB balanced disk.
* **Builder (method B):** a separate, disposable Rocky Linux 10.2 x86_64 host of the same size, with internet access.
* **Sinter:** v1.5.0 or later by the features the recipes use (see "Sinter version"); the real-host acceptance used
  a build of `main` after v1.5.1. The controller can be any host that can reach the target over
  SSH with `--sudo` (or a root login).
* **OpenStack:** 2026.1 (Gazpacho), built from the released source tarballs by the builder.

## Security limitations

This recipe is a verification demo. It keeps the choices of the installer it ports, and these are **not** safe
defaults for production:

* **SELinux is set to permissive** (now and at boot). Enforcing is not verified: no OpenStack SELinux policy is
  installed.
* **The OpenStack RPMs are unsigned**, and the self-built, NFV SIG and RDO repositories use `gpgcheck=0`.
  `rpm -K --nosignature` (used to check the build) verifies the package digests only; it is **not** a signature
  check. Integrity between the builder and the target is checked with SHA-256 (see "Verifying the staged RPMs").
* **firewalld is left as the image ships it.** The accepted cloud image's default zone was `trusted`, so the host
  firewall accepted every port; access was limited only by the cloud network's firewall.
* **Every service listens on the management network.** Anything that can reach the management address (for example
  other hosts in the same VPC) can reach MariaDB, RabbitMQ, the APIs and Horizon. Keep the node on an isolated
  network and **never expose the APIs or Horizon to the internet** without your own TLS, firewall and access
  control. Some local listeners (the RPM repository on 127.0.0.1) are unauthenticated.
* **Secrets** are generated by `tools/gen-secrets.sh` into the gitignored `secrets/` on the machine that runs
  Sinter, marked `sensitive`, and rendered into root-only files on the target. Protect both machines accordingly;
  `secrets.example/` contains synthetic values for CI only and must never be used.

## Getting the RPMs: build them (no RPMs are distributed)

Nobody publishes OpenStack 2026.1 RPMs for EL10, and **this project distributes none**: no RPM or RPM archive is
part of the repository, a Sinter release or the documentation site. Build them yourself from the upstream sources
on a disposable builder:

| | Method B (recommended) | Method A |
|---|---|---|
| RPMs | build with `builder.yaml` on a disposable Rocky 10.2 host (about an hour) | an archive **you** built earlier with Method B and kept, with its `SHA256SUMS` |
| Stage them on the target | `tools/stage-rpm-repo.sh --from-builder BUILDER --host TARGET` | `tools/stage-rpm-repo.sh --archive … --sums SHA256SUMS --host TARGET` |
| Then (both) | edit `site.yaml` → `tools/gen-secrets.sh` → `sinter validate/plan/apply all-in-one.yaml` | same |

`all-in-one.yaml` is the single OpenStack recipe for both methods; nothing about OpenStack is configured twice.
The built RPMs are a local artifact: keep them out of Git and do not redistribute them unless you have checked
the licenses of everything they bundle.

### Verifying the staged RPMs

Method B streams the repository without a checksum of its own. Record the builder's list, then check it on the
target after staging (both commands as root):

```sh
# on the builder
list=$(mktemp) && (cd /root/rpmbuild/RPMS && sha256sum noarch/*.rpm repodata/*) > "$list" && echo "$list"
# copy that file to the target (any private path, here ~/rpm-sha256.txt), then on the target
cd /opt/hagistack-repo && sha256sum -c ~/rpm-sha256.txt
```

Every line must end in `OK`. A build is usable only when `/var/lib/hagistack-build/build.ok` exists, the repodata
is present and `rpm -K --nosignature` passes for every RPM.

Method A expects an archive with a single top directory that holds `repo/` (the RPMs and `repodata/`) and
`SHA256SUMS.repo` (the SHA-256 of every file under `repo/`, with paths relative to `repo/`), plus a separate `SHA256SUMS` listing the archive itself;
build it yourself from a verified method-B repository if you want to keep one.

## Sinter version

The recipes need Sinter v1.5.0 or later. v1.4.0 brought `rpm -qp --nosignature` for RPMs signed with a key that is
not installed, parsing of dnf's wrapped long package names, and file management as root inside directories owned by
service accounts (with v1.3.0 `apply` stops with `payload verification produced unexpected stderr`,
`cannot establish the install transaction set` or `parent path … outside the trusted set`). v1.5.0 fetches absent
dnf metadata before an install itself, so the recipes no longer run `dnf makecache`. Every package name the recipes
use is a real package name (`%{NAME}`) in the repositories above, so v1.5.1's refusal of names that dnf reaches only
through a provides match does not apply.

## What is here

| File | Role |
|---|---|
| `all-in-one.yaml` | controller + compute on one node (the acceptance target) |
| `controller.yaml` | controller role only (no hypervisor, no `nova-compute`) |
| `compute.yaml` | an additional compute node (nova-compute, OVN chassis, metadata agent) |
| `builder.yaml` | Method B: builds the 2026.1 RPM repository with hagistack's `build-rpms.sh` on a *disposable* builder |
| `site.yaml` | non-secret settings: **edit the values marked `EDIT`** |
| `components/*.yaml` | one file per hagistack phase; included by the entry points |
| `templates/*.tpl` | configuration files rendered by Sinter (`template` resources) |
| `files/ensure.sh` | the imperative steps no resource type can express (DB/user creation, schema sync, Keystone/Nova/Neutron objects, OVS/OVN settings); each prints `changed`/`unchanged` |
| `tools/gen-secrets.sh` | generates `secrets/controller.yaml` and `secrets/compute.yaml` (gitignored); needs `openssl`, checks every value and writes neither file when a value cannot be generated or a file already exists |
| `tools/stage-rpm-repo.sh` | verifies an archive you kept (Method A) or streams the builder's repository (Method B) and puts it in `/opt/hagistack-repo` on the target |

`all-in-one.yaml` is `controller.yaml` ∪ `compute.yaml` (plus `wait_compute_up`, `nova_discover_hosts`, minus `compute_reach_controller`) with no resource managed twice (tested).

## Steps

1. **Stage the RPM repository on the target** in `/opt/hagistack-repo` (Method A or B above). The recipes serve that
   directory over loopback HTTP (`components/repo-local.yaml`; `repo_url` points to it).
   **`file://` repositories do not work with Sinter's `package` resource** (dnf uses them in place, so no payload
   reaches Sinter's snapshot).
2. **The target**: see "Requirements" (Rocky Linux 10.2 x86_64, 4 vCPUs, 16 GB RAM, about 50 GB free disk,
   `/dev/kvm` for `virt_type: kvm`), a **short hostname equal to `os_hostname`**, the address `mgmt_ip` on one of
   its interfaces, `dnf-plugins-core` installed. Before anything changes, the `preflight_*` resources check the OS
   (Rocky Linux 10.x, x86_64), the hostname, the address, `/dev/kvm` and `dnf-plugins-core`; they do not check
   memory or disk.
3. Edit `site.yaml` (`mgmt_ip`, `controller_ip`, `os_hostname`); run `sh tools/gen-secrets.sh` on the machine you
   run Sinter from (`secrets/` is gitignored; never commit it).
4. Run:

```sh
sinter validate all-in-one.yaml
sinter plan     all-in-one.yaml --host <node> --user <user> --sudo   # most of a first plan is Unknown, see below
sinter apply    all-in-one.yaml --host <node> --user <user> --sudo   # about 21 minutes on n2-standard-4
sinter apply    all-in-one.yaml --host <node> --user <user> --sudo   # rerun: expect 0 changed
sinter audit    all-in-one.yaml --host <node> --user <user> --sudo   # expect no_drift
```

(`--host` takes an SSH host or `~/.ssh/config` alias; see `sinter apply --help`.)

## Things to know

* **Plan is mostly "Unknown" on a fresh host.** Plan never runs commands, and a resource that depends on a
  command (the repository check, DB creation, schema sync ...) is Unknown too. About 160 of 172 resources in
  the all-in-one plan are Unknown on an empty host (and still about as many on a converged one: most of them hang
  below the read-only repository check, a `command`). That is correct, not a failure.
* **Package-created accounts.** Files owned by `keystone`, `glance`, `nova` ... name accounts that the RPMs
  create. Sinter cannot predict package-created accounts, so these files are ordered after the packages and,
  on a fresh host, kept Unknown by their command dependencies. This is a recipe-level workaround, not a Sinter
  feature (the dependency semantics are pinned by `tests/openstack_dependency_semantics.rs`).
* **No automatic restart on config change.** A changed `nova.conf` etc. triggers its handlers (`notify`) once
  at the end of the apply; services are *not* restarted by dependency order alone. The mapping from config
  files to handlers is part of the tests.
* **A failed apply loses the pending restarts.** Handlers run only at the end of a *successful* apply. If an
  apply changes a config file and then fails, the file is right on the rerun, nothing is notified and the running
  service keeps the old configuration (reproduced on a real host with mariadb). After a failed apply that had
  changed configuration, restart the affected services by hand. A permanent fix is designed but not implemented.
* **Secrets** are Sinter `sensitive` variables from the gitignored `secrets/*.yaml`, rendered into root-only
  files (`/etc/sinter-openstack/secrets.env`, `admin-openrc`, service configs). They are generated, never
  defaults. Rotating needs a deliberate action: the helper never overwrites an existing database/user password.
* **SELinux** is set to permissive now and at boot (`/etc/selinux/config`, as hagistack does): permissive is
  the only verified mode; Enforcing is not, because no OpenStack policy is installed.
* Not included: Horizon console/noVNC, a provider NIC attached to `br-ex`, HA, multi-region, upgrade tests.

## Real-host acceptance (2026-10-17)

GCE, Rocky Linux 10.2 x86_64: a disposable builder (method B; 195 RPMs) and an all-in-one node (`n2-standard-4`,
nested virtualization). Sinter was built from source on the builder (the `main` branch after v1.5.1) and drove the
all-in-one node over SSH with `--sudo` from that Linux host.

| Step | Result |
|---|---|
| `builder.yaml` | 13 changed, 0 failed (about 40 minutes); the staged repository matched the builder's SHA-256 list |
| First `apply` | 141 changed, 0 failed, 0 indeterminate (172 resources) |
| Second `apply` | 0 changed |
| `audit` | 81 compliant, 0 drifted, 91 not_auditable (every `command` resource; audit does not run commands, so these are not counted as compliant) |
| Reboot, then `apply` | all services came back; 0 changed; `audit` again no drift |
| OpenStack | Keystone token, all API endpoints, Nova conductor/scheduler/compute up, OVN agents and chassis, Glance image active, Horizon login |
| Guest | CirrOS 0.6.3 `ACTIVE` under KVM, ping 0% loss and SSH (host key checked) from the metadata namespace, also after the reboot |

The published recipe differs from the accepted one in two places, both covered by tests and **not** run on a real
host:

* The Keystone key steps (`keystone-manage fernet_setup` / `credential_setup` in `files/ensure.sh`) now run through
  the helper's logged runner, so their own output no longer hides a real change (the accepted run reported them as
  unchanged although it created the keys), and on a failure the output is shown only on stderr, shortened.
* `tools/gen-secrets.sh` (run on the controller, not on the target) now stops with an error and writes no file when
  `openssl` is missing or fails, or a value is not 32 characters of A-Za-z0-9; the earlier version could write empty
  values. It also refuses an existing `secrets/compute.yaml` or symbolic link, places the files only when both are
  complete, and never replaces a file (see the comment at the top of the script). The accepted run used the earlier
  version, with `openssl` present.

## Still unverified

`controller.yaml` and `compute.yaml` on separate hosts and any multi-node setup; SELinux Enforcing; `%check` of
the RPMs; `gpgcheck=1` repositories with this RPM set (a signed test repository was checked separately); externally
reachable guests (floating IPs); upgrades; a released Sinter binary (the acceptance used a build of `main`); and
whether the external repositories (RDO's floating trees, the NFV SIG mirror, EPEL) still give the same result
later.

Found on real runs and fixed in these recipes: cold dnf cache (first worked around with `dnf makecache`
commands, which Sinter v1.5.0 made unnecessary: a package install fetches absent metadata itself), RDO repo files and a two-pass build
for the builder, the incomplete self-built `python3-cliff` (EPEL's is used), `ovn-sbctl get-connection` output
format, OVS `system-id` and libvirt (modular daemons) across reboots, `/etc/openvswitch` being owned by
`openvswitch` (Sinter's FS-3 rule), and `file://` repositories being unusable (loopback HTTP instead).
